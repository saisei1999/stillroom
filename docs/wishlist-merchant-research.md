# Wishlist merchant enrichment feasibility

Initial findings for [PER-67](https://linear.app/halcyonnetwork/issue/PER-67). The [Wishlist scope](wishlist.md#merchant-offers-prices-and-shipping) calls for a shared fetcher for public product pages, no paid enrichment subscription, and optional destination data. Shopify is a representative source for testing the shared path.

## Shared fetcher direction

Accept product links from any store and save them first. Send eligible links through one fetch and parse path that reads public page metadata. Use structured `Product`, `ProductGroup`, and `Offer` data when available. Page title and social preview metadata can supply a name and image when they describe the linked product. A verified site icon or Stillroom’s generic merchant icon can represent the store. Take price and currency from an unambiguous offer for the selected variant. Optional shipping fields apply only when the offer, shipping conditions, and destination match. [Merchant listing markup](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing), [variant markup](https://developers.google.com/search/docs/appearance/structured-data/product-variants/)

Check the same parser against permitted pages from different storefronts. Fixtures should cover a precise offer, variant-specific prices, a product group with only a price range, a page with title and image only, and an offer with destination-specific shipping. Also verify that a blocked page or unavailable network leaves the saved link usable. Keep a permission policy for sources while reusing the same extraction logic across them.

Browser reads depend on cross-origin access from the merchant. Compare direct browser fetch against a single controlled service or a user-initiated browser capture if wider access is necessary. Validate permissions, data sent, storage, and deployment cost before choosing a transport. The shared fetch path must respect site restrictions. Amazon remains link-only until a permitted page source is verified for this use. The API comparison below records why merchant accounts and integrations are outside the proposed architecture. [Fetch CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol), [Amazon Associates policies](https://affiliate-program.amazon.com/help/operating/policies)

## Amazon retail

**Decision for the current scope:** keep Amazon as a saved product link with manual fields. There is no verified official Amazon retail source that fits both the personal Wishlist use and its durable storage model.

| Source | Documented capabilities | Fit for Stillroom |
| --- | --- | --- |
| Amazon Associates Creators API | GetItems looks up a specific ASIN with title and image URLs. GetVariations enumerates child products. OffersV2 can return featured listing price, currency and merchant information. It does not return arbitrary seller listings, and the field mapping explicitly omits shipping charges. No destination-specific arrival estimate was verified in the catalog documentation. | Requires Associates acceptance, credentials and the published qualifying-sales threshold for access. Amazon restricts use to applications whose principal purpose is promoting Amazon and driving its sales. Local caching and backup of API product data also conflict with the client storage restriction. [Prerequisites](https://affiliate-program.amazon.com/creatorsapi/docs/#prerequisites), [catalog reference](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/api-reference), [featured offers and shipping fields](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/api-reference/resources/offersV2), [program policies](https://affiliate-program.amazon.com/help/operating/policies) |
| Amazon Business Product Search | Product and offer lookup with documented shipping region and postal code personalization for estimated shipping cost and delivery time. | A separate procurement integration. It requires developer onboarding, tokens, the Business Product Catalog role and a consenting Amazon Business group. This would change Stillroom's account and destination data requirements. [Product Search](https://docs.business.amazon.com/docs/product-search-api-overview), [shipping personalization](https://docs.business.amazon.com/docs/personalizing-searches) |

Amazon's Associates policies generally allow server caching of eligible non-image product content and image links for up to 24 hours, with refresh requirements and a pricing timestamp rule. They prohibit caching image bytes and client-side caching of Product Advertising Content. If approval and compatible use terms ever justify revisiting this source, verify account quotas, keep credentials server-side, and keep API data out of local backups unless Amazon explicitly permits that use. The current link-only path needs no API cache, API calls or destination data. Use Stillroom's generic merchant icon until permitted Amazon branding is verified. [Associates program policies](https://affiliate-program.amazon.com/help/operating/policies), [API rates](https://affiliate-program.amazon.com/creatorsapi/docs/en-us/concepts/api-rates)

Evidence is from first-party documentation. No live catalog request, Amazon page extraction, or destination quote was performed. Keep the user-supplied URL and its variant parameters. If a short link is saved, open it in the browser at the user's request and leave it unexpanded in storage. For a future authorized integration, compare two distinct child ASINs, a parent ASIN, a listing with no featured offer, and a seller-specific offer. Match marketplace, child ASIN and seller before accepting a price. Leave price, shipping and arrival Unknown whenever the source cannot establish them.

## What was observed

Public pages from Shopify's Dawn demo expose titles, product images and visible CAD prices for a sandal with size/color choices and a bag with color choices. The pages also show store-wide shipping copy, including a transit estimate measured from shipment. A direct request from the development environment failed before returning headers, so raw markup, favicon retrieval and browser CORS remain unverified. Exact selection-to-price binding and postal-specific quotes are also pending. The demo publishes crawlable product HTML and directs agents to supported interfaces for shopping actions. Its catalog discovery URL could not be read in this check. No live eBay or Best Buy API call was made, and no accounts, addresses or carts were used. [Sandal](https://theme-dawn-demo.myshopify.com/products/louise-slide-sandal), [bag](https://theme-dawn-demo.myshopify.com/products/small-convertible-flex-bag-cappuccino), [crawl policy](https://theme-dawn-demo.myshopify.com/robots.txt), [supported demo interfaces](https://theme-dawn-demo.myshopify.com/agents.md)

### Cross-store feasibility check

The official WooCommerce Purple demo showed the Cashmere Blend Scarf at a displayed sale price with five color choices, product images, and a free-shipping banner conditioned on order value. This did not establish a price for a linked color or a destination-specific quote. Another demo product returned HTTP 429 in the research tool, and inspection stopped there. WooCommerce’s markup generator documents distinct behavior for selected variations and parent products, which informed the fixtures. Shopify Dawn’s guidance allows public browsing and requires identification for automated requests. No further direct raw-page requests were attempted without confirmed access. [Purple demo product](https://purpledemo.wpcomstaging.com/product/lightweight-cashmere-blend-scarf/), [WooCommerce markup source](https://github.com/woocommerce/woocommerce/blob/trunk/plugins/woocommerce/includes/class-wc-structured-data.php), [Dawn agent guidance](https://theme-dawn-demo.myshopify.com/agents.md)

Run `python scripts/wishlist-metadata-feasibility.py` from the repository. The offline probe uses synthetic HTML based on standard markup and the documented patterns, with one parser shared by every fixture. It makes no network requests. The 16 verified cases cover:

| Fixture | Result |
| --- | --- |
| One exact offer in a JSON-LD graph | Title, image and a CAD price |
| Two directly linked variants | Separate CAD 20 and CAD 25 offers. Parent URL leaves price Unknown |
| Aggregate range or two ambiguous matching listings | Price Unknown |
| Product social preview and same-origin favicon | Title, image and icon URL, with price Unknown |
| A flat explicit zero shipping rate for one synthetic Canadian postal code | CAD 0 for the matching destination, Unknown for a different postal code, country or missing destination |
| A national delivery rule with an explicit postal exclusion | No shipping price or delivery estimate for the excluded postal code. The country-wide rate works for another postal code. Without a code, the exclusion cannot be ruled out and no quote is shown. |
| Handling of 1–2 days plus transit of 2–5 days | A relative 3–7 day test result. This does not establish a calendar arrival date or account for business days |
| Empty or blocked response body and unsupported image URL | No enrichment for the blocked fixture. Unsafe image URL omitted |

The probe uses exact offer/product URL matching, including query parameters, and restricts shipping to simple recognized fields. These fixtures do not verify coverage on a real storefront. Linked JSON-LD references, price specifications, unknown shipping conditions and date conversion need separate support before production use. The probe reads favicon URLs but does not retrieve image bytes or establish usage rights.

A separate isolated Chrome test used two localhost origins. An anonymous cross-origin request read the expected HTML when the fixture returned `Access-Control-Allow-Origin: *`. The same request without that header raised `TypeError` with no readable body. This validates the transport boundary in Chrome. Neither demo merchant’s CORS behavior was measured. [Fetch CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol)

### Transport and retention decisions still open

The narrowest automatic candidate is a browser fetch for verified, eligible sources that permit access from Stillroom’s origin. Use the same parser for each source. Other pages stay available as saved links and can use manual fields. A broader automatically fetched set would need either a controlled service or an explicit browser capture workflow, with its own approval and source permissions. No public proxy, extension installation or hosted service is part of this probe.

Compare costs against a small, bounded pilot. Proposed limits for testing are one outstanding lookup per offer, a five-second timeout and a 1 MiB HTML limit. Respect each source’s stricter limits and retry guidance. As a starting proposal, refresh price and shipping after one hour and title and image metadata after 24 hours, subject to shorter permitted retention. Retention and backup permission need their own checks before any observations are persisted. Keep user-entered values and the original link independently of the cache, and use a failed or expired result only where permissions and freshness allow. The direct-page candidate can match prepublished shipping conditions against optional country and postal code locally. No address data needs to leave the device for that comparison.

### Live name and image check

Made read-only HTTPS requests without cookies, destination data, or redirect following to storefronts that expressly invite this kind of testing. These were live pages with demo products. Requested each page with the Stillroom Pages origin and checked its response headers, then ran the same offline parser over the returned HTML.

| Page or condition | Observed result |
| --- | --- |
| TestingURL.dev catalog product | HTTP 200, 57,180 bytes. The exact offer URL matched. The parser returned Vertex Air Laptop 107, its product image URL, USD 86.00 and a storefront icon URL. Chrome decoded the product image at 600 × 450. |
| TestingURL.dev separate format demos | All four returned HTTP 200. The JSON-LD and combined examples pointed at the catalog URL, so the parser did not assign their offers to the pasted demo URLs. The social preview fields did not establish the same product, and the microdata-only page is outside current parser coverage. |

To replay permitted HTML locally, run `python scripts/wishlist-metadata-feasibility.py --html <snapshot-file> --url <original-product-url>`. The script parses only the local file. The live tests established that standard metadata can produce the name and image when HTML is available, and the original input supplies the clickable product link. They did not establish general live retail coverage or live shipping quotes.

For automatic enrichment after paste on desktop and mobile, the proposed transport is one controlled fetch service. Direct browser fetch is a limited option for stores explicitly permitting cross-origin reads. Browser capture would add an extra user action and requires a separate extension decision. Amazon remains link-only pending a permitted source.

### Verified local service pilot

Run `python scripts/wishlist-metadata-pilot.py`, open `http://127.0.0.1:5198/` and paste `https://testingurl.dev/scraping/ecommerce/product/1` into Product URL. The preview shows the original link immediately, then uses the existing shared parser's returned title and image. In a disposable Chrome profile at 390 × 844, native Ctrl+V displayed **Vertex Air Laptop 107** as the link text and a **600 × 450** image. An unsupported URL and a simulated upstream failure both kept the original link usable. This preview is separate from Wishlist storage. [Permitted test storefront](https://testingurl.dev/)

The service listens on loopback and accepts requests from its own origin. It accepts exactly one JSON field, `url`, and fetches only the specific permitted test URL. It checks that the chosen address is public before connecting to it with normal TLS verification, rejects redirects, bounds the HTML body to 1 MiB, and throttles outbound lookups. Browser calls and upstream fetches use no cookies or destination data. The pilot keeps no request logs or cache. It only returns the title and same-source image URL from the markup. Chrome and HTTP checks confirmed the URL-only payload, rejection of other origins and extra fields, and the link-only fallback. An isolated resolver fixture confirmed that a non-public result is rejected before connecting. All 13 parser fixtures passed.

This establishes that the controlled service can read a permitted page whose HTML is unavailable to direct browser fetch. PER-69 still needs the Wishlist integration, a deployment and origin policy, production limits and monitoring, and eligibility checks for the first supported retailers. The pilot exercised one demo product. Live retailer coverage, destination-specific shipping and the hosted transport remain unverified.

## Boundaries for the next check

- **Source and variant.** Compare a single-variant URL, two directly linked variants with different prices, and an ambiguous product URL on a permitted storefront. Verify currency and availability as well as price. Where permitted HTML exposes structured data, require an exact `Product` and `Offer` match before using its price or optional `shippingDetails`. A generic shipping banner, shipment lead time or product-group price range leaves the relevant offer field Unknown. Use a generic merchant icon until a permitted store favicon or brand asset is verified. [Variant markup](https://developers.google.com/search/docs/appearance/structured-data/product-variants/), [offer shipping fields](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing#shipping)
- **Privacy and network.** Keep country and postal code optional and local by default. Before sending them, disclose their recipient and purpose. Leave shipping Unknown when an endpoint needs more destination data or the user leaves it blank. Verify cross-origin reads from Stillroom's actual origin. If a backend is considered, use allowlisted HTTPS merchant routes with bounded response size and timeouts. Validate DNS and each permitted redirect against the allowlist and reject private or special-use addresses. Treat returned text and image URLs as untrusted data and keep merchant credentials server-side. [Fetch CORS protocol](https://fetch.spec.whatwg.org/#http-cors-protocol), [IANA IPv4 registry](https://www.iana.org/assignments/iana-ipv4-special-registry), [IANA IPv6 registry](https://www.iana.org/assignments/iana-ipv6-special-registry)
- **Cache and freshness.** Choose source-specific staleness thresholds before enabling refresh on capture and stale item open. Application staleness and permitted retention need separate limits. Shopify Catalog, for example, allows up to 10 minutes for price/availability and 24 hours for titles/options and Shopify CDN images. Confirm each source's retention rules for backups, then key permitted observations by source, offer, variant and market, plus destination for shipping. Coalesce refreshes, cap calls per merchant and back off when throttled. Keep the source and last-checked time, preserve manual overrides, and show stale values only while retention terms permit. A failed refresh preserves the offer and never implies free shipping or a guaranteed arrival. [Shopify Catalog limits](https://shopify.dev/docs/agents/catalog), [Best Buy API terms](https://developer.bestbuy.com/legal)
